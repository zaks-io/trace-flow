### Non-blocking gaps and recommendations

- **G1. Missed copied-header boundary: MCP Worker to Convex (confidence 8/10).**
  - **Where:** `apps/mcp/src/index.ts:130-137` (`proxyConnect`: `new Request(url, c.req.raw)`) and `:139-173` (`proxyToken`: `new Headers(c.req.raw.headers)`). Both forward every header from an external MCP client, including `sentry-trace`, `baggage`, `traceparent` and `tracestate`, to `CONNECT_BASE_URL` (Convex). They serve `OAUTH_METADATA_PATH`, `/mcp/register` and `/mcp/token` (`:290-300`).
  - **Why it matters:** this is the same class of leak the audit fixed for providers. The audit itself says an SDK allowlist alone can't strip copied headers (`audit.md:99`), yet row `:114` says "Fixed" for MCP to Convex, which reads as complete isolation. The `connect.trace-flow.dev` exclusion only stops headers the SDK adds itself. Convex's `httpRoutes/shared.ts:19` then reads the forwarded `traceparent` into domain log context (reserved baggage keys are stripped, `logging/src/index.ts:476`).
  - **Direction:** record it in the audit as an open copied-header boundary. The smallest fix is to strip the trace header set in these two proxies, ideally reusing one shared list with `forwardToUpstream`. Whether that lands in this slice or a follow-up is your call.

- **G2. The new log field inherits the open ingress-trust question.** `sentry_trace_id` and `sentry_span_id` come from whatever SDK span is active. At the gateway and the MCP ingress that span can continue a context the caller supplied (`sentry-runtime.integration.test.ts:37-59`), and an unsampled caller header produces IDs with no Sentry trace behind them (test `sentry-context.test.ts:178-189`). The P2 trust row (`audit.md:132`) covers the policy itself. I'd add one sentence to row `:68` saying log readers shouldn't treat the field as server-originated until that policy is decided.

- **G3. The synthetic errors throw away all diagnostic signal.**
  - **Where:** `handler.ts:144-152`, `bodies.ts:140-149`, `proxy-consumer/src/index.ts:402-410,427-434`.
  - **Why it matters:** in Sentry, a misconfigured body key, corrupt JSON, an R2 outage and a Tinybird 5xx all look identical. In MCP the console log loses its cause too.
  - **Direction:** keep the payload protection, but add a tag that is safe by construction. Examples: built-in `error.name` checked against an allowlist (`SyntaxError`, `OperationError`, `TypeError`, `AbortError`), or a numeric HTTP status where the error type exposes one. The audit's trade-off sentence (`:139-140`) already admits the loss, so this is optional.

- **G4. Raw errors are still logged right next to the new privacy comments.** `index.ts:403,428` and `bodies.ts:141` still pass the raw error to `logger.error`, which sends it to console and Axiom. V8 `JSON.parse` messages include a slice of the input. These calls existed before this change and the audit acknowledges them (`:134`, "Broader existing-log cleanup remains"). Still, the new comment "Parser errors can include customer payload fragments" sits beside a call that persists those fragments. The follow-up should be tracked explicitly.

- **G5. Exact `@sentry/core` pins against caret app pins can fail silently.** `packages/logging/package.json:17` and `packages/mcp-core/package.json:17` pin `10.73.0` exactly. Apps use `^10.73.0` for `@sentry/cloudflare`. If only part of the tree is upgraded later, two `@sentry/core` copies with different version-keyed carriers would appear. `getActiveSpan()` would then quietly return nothing, and the scope-less `captureException` in mcp-core would quietly do nothing, contrary to fail-loud. `tinybird-client` and `convex` already set this precedent, so it isn't new risk, just more of it. Consider making `@sentry/core` a peer dependency for these library packages, or note the upgrade constraint in the SDK migration slice (`audit.md:167-170`).

- **G6. Test fidelity.** The continuation suite's `withSentry` mock adds `skipOpenTelemetrySetup: true` and unwraps the TraceBatcher DO (`queue-trace-continuation.integration.test.ts:31-41`). Production does neither. That's acceptable for checking consumer scopes, and the audit already says queue-to-DO RPC linkage is unproven. It would be worth one clause that the OTel-setup difference also hasn't been exercised.

- **G7. Precision of the memory claim.** The comment at `index.ts:414` and the audit at `:101` suggest a memory improvement. The baseline already resolved envelopes one by one inside each group. What the new code actually avoids is resolving everything up front just to regroup by the envelope's context. Suggested wording: "Resolving per envelope avoids pre-loading a batch to regroup by envelope context."

- **G8. Minor robustness and style.**
  - In the inline loop (`index.ts:445-446`), `resolveQueueItem` now runs outside `processMessage`'s try. It can't throw for inline payloads today, but if it ever did, the whole batch would fail instead of just that message being retried.
  - `ResolvedMessage.resolved` (`:379-382`) restates `ResolvedQueueItem`; the existing interface could be used.
  - Delivery transactions are now one per envelope, so many Proxy requests sharing a caller-supplied `sentry-trace` no longer group together. That's more transactions, not a correctness problem.
